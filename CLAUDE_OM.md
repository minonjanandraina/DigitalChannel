## Schéma des tables externes `interop_om_*` (managed = False côté Django)

The following tables were created manually and must be mapped to Django models with `managed = False`
(même principe que `interop_mvola_*` dans `mvola/models.py`: écrites uniquement par `service_om.py`
via SQLAlchemy/pandas `to_sql`, jamais par l'ORM Django).

```sql
-- le process de rapprochement démarre ici (classe Django: InteropOmProcess)
CREATE TABLE public.interop_om_process (
	id int8 NOT NULL GENERATED BY DEFAULT AS IDENTITY( INCREMENT BY 1 MINVALUE 1 MAXVALUE 9223372036854775807 START 1 CACHE 1 NO CYCLE),
	"userID" int8 NOT NULL,
	"Status" text NOT NULL,
	"insertDate" timestamptz NOT NULL DEFAULT now(),
	transaction_date date NULL,
	CONSTRAINT interop_om_process_pkey PRIMARY KEY (id)
);

-- données brutes Orange Money (classe Django: InteropOmOm)
CREATE TABLE public.interop_om_om (
	"No" int8 NULL,
	"date" text NULL,
	"hour" text NULL,
	trx_id text NULL,
	service text NULL,
	transaction_type text NULL,
	status text NULL,
	"mode" text NULL,
	technical_account text NULL,
	wallet_technical_account text NULL,
	pseudo text NULL,
	client_account text NULL,
	wallet_type text NULL,
	debit text NULL,
	credit text NULL,
	commission_amount int8 NULL,
	sous_reseau int8 NULL,
	id int4 NOT NULL GENERATED ALWAYS AS IDENTITY( INCREMENT BY 1 MINVALUE 1 MAXVALUE 2147483647 START 1 CACHE 1 NO CYCLE),
	process_id int8 NULL,
	CONSTRAINT interop_om_om_pkey PRIMARY KEY (id),
	CONSTRAINT fk_interop_om_om_process FOREIGN KEY (process_id) REFERENCES public.interop_om_process(id) ON DELETE CASCADE
);

-- données brutes CBS (classe Django: InteropOmCbs)
CREATE TABLE public.interop_om_cbs (
	"apiLogId" text NULL,
	"PostingDate" text NULL,
	"AmountCRY" float8 NULL,
	trx_id text NULL,
	id int4 NOT NULL GENERATED ALWAYS AS IDENTITY( INCREMENT BY 1 MINVALUE 1 MAXVALUE 2147483647 START 1 CACHE 1 NO CYCLE),
	process_id int8 NULL,
	CONSTRAINT interop_om_cbs_pkey PRIMARY KEY (id),
	CONSTRAINT fk_interop_om_cbs_process FOREIGN KEY (process_id) REFERENCES public.interop_om_process(id) ON DELETE CASCADE
);

-- résultat du rapprochement, reconciliation_status -> orphan_om, orphan_pamf, matched (classe Django: InteropOmReconciliation)
CREATE TABLE public.interop_om_reconciliation (
	"No" int8 NULL,
	"date" text NULL,
	"hour" text NULL,
	trx_id text NULL,
	service text NULL,
	transaction_type text NULL,
	status text NULL,
	"mode" text NULL,
	technical_account text NULL,
	wallet_technical_account text NULL,
	pseudo text NULL,
	client_account text NULL,
	wallet_type text NULL,
	debit text NULL,
	credit text NULL,
	commission_amount int8 NULL,
	sous_reseau int8 NULL,
	"apiLogId" text NULL,
	"PostingDate" text NULL,
	"AmountCRY" float8 NULL,
	reconciliation_status text NULL,
	id int4 NOT NULL GENERATED ALWAYS AS IDENTITY( INCREMENT BY 1 MINVALUE 1 MAXVALUE 2147483647 START 1 CACHE 1 NO CYCLE),
	process_id int8 NULL,
	CONSTRAINT interop_om_reconciliation_pkey PRIMARY KEY (id),
	CONSTRAINT fk_interop_om_reconciliation_process FOREIGN KEY (process_id) REFERENCES public.interop_om_process(id) ON DELETE CASCADE
);
```

Même principe que `interop_mvola_*`: les FK `interop_om_*` sont en `ON DELETE CASCADE`, donc supprimer une ligne
`interop_om_process` supprime automatiquement les lignes `interop_om_om/cbs/reconciliation` associées.

**À appliquer manuellement sur la base PostgreSQL réelle** (ces tables sont créées et modifiées hors migrations Django,
donc hors de portée de ce dépôt): les contraintes existantes doivent être recréées en `ON DELETE CASCADE` si elles ont
été créées en `ON DELETE SET NULL`, par exemple:

```sql
ALTER TABLE public.interop_om_om
    DROP CONSTRAINT fk_interop_om_om_process,
    ADD CONSTRAINT fk_interop_om_om_process
        FOREIGN KEY (process_id) REFERENCES public.interop_om_process(id) ON DELETE CASCADE;

ALTER TABLE public.interop_om_cbs
    DROP CONSTRAINT fk_interop_om_cbs_process,
    ADD CONSTRAINT fk_interop_om_cbs_process
        FOREIGN KEY (process_id) REFERENCES public.interop_om_process(id) ON DELETE CASCADE;

ALTER TABLE public.interop_om_reconciliation
    DROP CONSTRAINT fk_interop_om_reconciliation_process,
    ADD CONSTRAINT fk_interop_om_reconciliation_process
        FOREIGN KEY (process_id) REFERENCES public.interop_om_process(id) ON DELETE CASCADE;
```

Une fois le `CASCADE` en place, les suppressions explicites par table dans `service_om.delete_existing_process_data()`
deviennent redondantes avec la suppression finale de la ligne `interop_om_process` (qui cascaderait seule), mais
restent sans danger — aucun changement requis côté `service_om.py` pour ce point.

## Flux fonctionnel

1. L'utilisateur importe depuis le web le rapport Excel Orange Money, nommé
   `Daily-ChannelUserTransactionReport-0324660679-yyyymmdd.xls`
   (ex.: `Daily-ChannelUserTransactionReport-0324660679-20260912.xls`).
2. Le fichier est enregistré dans `input/om/` (répertoire piloté par la variable d'environnement `OM_INPUT_DIR`,
   voir "Configuration").
3. La liste des fichiers de `input/om/` est affichée avec un bouton "Lancer".
4. Au clic sur "Lancer", la vue Django appelle directement et de façon synchrone
   `service_om.reconciliation(filename, user_id)` — même principe que `mvola` (pas de file d'attente, pas de tâche async).

## État actuel de `service_om.py` (au 2026-09-30)

- Les identifiants du process (`process_id`) et le comportement retraitement sont **différents de `service_mvola.py`**:
  `service_om.reconciliation()` appelle `delete_existing_process_data(transaction_date)` qui supprime toutes les lignes
  `interop_om_process`/`interop_om_om`/`interop_om_cbs`/`interop_om_reconciliation` de la même `transaction_date` **avant**
  de recréer un nouveau process et de ré-insérer les données. Un retraitement pour une date donnée remplace donc
  entièrement le rapprochement précédent de cette date (contrairement à `mvola`, où chaque lancement crée un nouveau
  process sans jamais supprimer les précédents).
- Bug de table corrigé (2026-09-30): `delete_existing_process_data()` interroge désormais bien `interop_om_process`
  (et non plus `interop_mvola_process`) dans ses trois sous-requêtes `DELETE ... WHERE process_id IN (SELECT id FROM ...)`.
- **Bug encore ouvert**: le dict retourné par `reconciliation()` en cas de succès ne contient toujours pas
  `process_id` (contrairement à `service_mvola.reconciliation`, qui le renvoie). **Contourné côté Django au Sprint
  OM-3** plutôt que bloquant: `om/views.py::_recover_process_id()` retrouve le `process_id` via
  `transaction_date` après un succès (voir Sprint OM-3 ci-dessous pour le détail). Une correction de
  `service_om.py` rendrait ce contournement inutile sans rien casser (le `process_id` du résultat du service
  prime toujours sur le contournement), mais n'est plus bloquante pour la suite.
- Identifiants PostgreSQL (`get_pg_engine`, `delete_existing_process_data`) et CBS (`get_connection`) toujours codés en
  dur dans `service_om.py`. Comme pour `service_mvola.py` avant son Sprint 4, il faudra les faire lire depuis la
  configuration d'environnement avant tout usage en production — non traité ici tant que le fichier reste interdit
  d'accès pour ce point.
- `input_om` est lu depuis `OM_INPUT_DIR` (corrigé le 2026-09-30, auparavant lu depuis `MVOLA_INPUT_DIR` par erreur).
- Lecture `.xls` via `pandas.read_excel`: nécessite le paquet `xlrd`, **ajouté à `requirements-service.txt`
  (2026-09-30)**.
- **Structure réelle du fichier `.xls`** (vérifiée sur les rapports présents dans `input/om/`): ce n'est pas un tableau
  propre avec une ligne d'en-tête unique. Le fichier contient d'abord ~20 lignes de métadonnées (titre, application,
  réseau, période, date de génération), puis un ou plusieurs blocs de transactions, **chacun précédé de sa propre
  ligne d'en-tête** (`N°/Date/Heure/.../Statut/...`) et suivi d'une ligne `Total`. `read_om_transaction()` lit tout le
  fichier de façon positionnelle sur 17 colonnes (`names=cols_om`, donc `header=0`: seule la toute première ligne,
  vide, est sautée) puis filtre `status == 'Succès'` — ce qui fonctionne correctement en pratique car les lignes de
  métadonnées/en-têtes/totaux n'ont jamais exactement `'Succès'` dans la colonne 7 (`status`), mais ce n'est pas une
  lecture tabulaire "propre". `om/forms.py::OmReportUploadForm` reproduit cette même lecture positionnelle (mêmes 17
  colonnes, mêmes filtres `Succès`/`Echec`) pour que la validation à l'upload corresponde exactement à ce que
  `service_om.py` traitera réellement — voir le commentaire en tête de `om/forms.py`.

## Détail CBS d'une transaction orpheline (affichage côte à côte)

`mvola/views.py::_load_cbs_transaction` appelle `service_mvola.get_transaction_by_requestID(requestID)` pour afficher,
sur la page de détail d'une orpheline MVOLA, la requête/réponse CBS brute côte à côte avec la ligne MVOLA:

```python
def get_transaction_by_requestID(requestID):
    sql='''
    select top 1 requestID, RequestBody, RequestURL, ResponseBody from [bagsPAMF_CBS_MC].dbo.apiLog where requestID='{r}'
    order by apiLogId desc
    '''.format(r=requestID)
    df = pd.read_sql(sql, get_connection())

    if len(df) == 0:
        return None
    else:
        return df.to_dict(orient='records')[0]
```

`om/views.py` réutilise **cette même fonction, importée depuis `service_mvola`** (`from service_mvola import
get_transaction_by_requestID`) — elle n'est pas dupliquée dans `service_om.py`, la requête CBS `apiLog` étant commune
aux deux canaux. Contrairement à MVOLA où l'identifiant utilisé est `TRANSID_MVOLA`, côté OM l'identifiant à passer à
`get_transaction_by_requestID` est le **`trx_id`** de la ligne `interop_om_reconciliation` (c'est ce même `trx_id` qui
sert de clé de jointure OM/CBS dans `service_om.reconciliation()` — voir `pd.merge(..., left_on='trx_id',
right_on='trx_id', ...)`). La vue `om.views.orphan_transaction_detail` suit donc le même pattern que
`mvola.views.orphan_transaction_detail`/`_load_cbs_transaction`, en remplaçant `row.transid_mvola` par `row.trx_id`.

## Modèles Django à créer dans `om/models.py`

Même pattern que `mvola/models.py`:

- `InteropOmProcess`, `InteropOmOm`, `InteropOmCbs`, `InteropOmReconciliation` — `managed = False`, mapping direct des
  colonnes ci-dessus (FK `process` avec `on_delete=models.DO_NOTHING`, comme côté `mvola`, puisque Django ne gère pas
  ces tables). **Différence de taille de clé primaire par rapport à `mvola`**: `interop_om_process.id` est `int8`
  (→ `BigAutoField`, comme tous les `id` côté `interop_mvola_*`), mais `interop_om_om.id`, `interop_om_cbs.id` et
  `interop_om_reconciliation.id` sont en `int4` (→ `AutoField`, pas `BigAutoField`, pour rester fidèle au DDL réel).
- `ReconciliationRun` (app `om`) — même structure que `mvola.ReconciliationRun`
  (`requested_by`, `filename`, `status` en `queued/running/succeeded/failed`, `queue_task_id`, `process_id`, `message`,
  `created_at`, `started_at`, `finished_at`, permission `view_om_reconciliation_runs`). `requested_by` doit utiliser
  `related_name='om_reconciliation_runs'` (différent de `mvola_reconciliation_runs` côté mvola) pour éviter un conflit
  de related_name sur `settings.AUTH_USER_MODEL`, les deux modèles portant le même nom de classe `ReconciliationRun`
  dans deux apps différentes.
- `OrphanOmProcessingHistory` — **la FK doit pointer vers `InteropOmReconciliation`**, pas vers `InteropOmProcess`
  (le pseudo-code précédent de ce fichier était une coquille de copier-coller de `OrphanMvolaProcessingHistory`, qui
  pointe bien vers `InteropMvolaReconciliation` dans `mvola/models.py`). Champs, **identiques à
  `OrphanMvolaProcessingHistory`, sans champ utilisateur**: `processed_at` (auto_now_add), `is_retried`,
  `response_message`, `status` (`orphan_om`/`orphan_pamf`/`processing`/`done`), `comments`.
  (Le pseudo-code d'origine de ce fichier laissait entendre un champ `userID`, mais `OrphanMvolaProcessingHistory`
  n'en a pas — l'auteur de l'action de régularisation n'est pas tracé côté mvola; on garde la parité plutôt que
  d'ajouter un champ que mvola n'a pas.)

`ReconciliationRun` et `OrphanOmProcessingHistory` sont gérés par Django (migrations normales); les 4 modèles
`InteropOm*` restent hors migrations (`managed = False`), comme `interop_mvola_*`.

## Permissions et rôles

Même principe que `mvola` (`accounts/roles.py`): pas de permissions dédiées OM, on étend les rôles existants
(Viewer/Backoffice/Admin) avec de nouvelles capacités dans `CAPABILITY_NAMES`/`ROLE_CAPABILITIES`:

- `import_om_report` (Backoffice, Admin)
- `run_om_reconciliation` (Backoffice, Admin)
- `view_reconciliation_results` déjà existante est réutilisée telle quelle pour l'historique/détail om (Viewer,
  Backoffice, Admin) — pas de `view_om_transactions` séparée, ce serait redondant avec l'équivalent MVOLA déjà
  générique.

## Configuration (`.env` / `config/settings.py`)

- `OM_INPUT_DIR` (déjà lu par `service_om.py`, valeur par défaut `input/om/`) — à ajouter aussi côté `settings.py`
  Django, pour que la vue d'import Django et `service_om.py` pointent vers le même dossier
  (même schéma que `MVOLA_INPUT_DIR`).
- `OM_MAX_UPLOAD_SIZE` — taille max d'upload en octets, avec valeur par défaut proposée à **10 Mio**
  (`10 * 1024 * 1024`), configurable comme `MVOLA_MAX_UPLOAD_SIZE`. Les rapports `.xls` réels actuellement dans
  `input/om/` pèsent entre ~30 Ko et ~100 Ko: 10 Mio laisse une marge large (~100x) tout en évitant d'accepter des
  fichiers manifestement anormaux. À ajuster si des rapports beaucoup plus volumineux sont attendus en prod.
- Ajouter `xlrd` à `requirements-service.txt` (nécessaire à `pandas.read_excel` pour le format `.xls` binaire —
  confirmé).

## Historique de rapprochement et process orphelin

Comme pour `mvola`, `reconciliation_history` (om) interroge directement `interop_om_process` (vérité en base, pas
`ReconciliationRun`), donc un process supprimé par un retraitement disparaît naturellement de la liste — pas de
traitement spécial nécessaire. Le seul endroit où un `process_id` obsolète peut apparaître est le petit historique des
lancements affiché sur la page d'import (`ReconciliationRun.objects.filter(requested_by=...)`, qui n'est jamais purgé).
Si l'utilisateur clique vers le détail d'un process qui n'existe plus, on applique le même principe que
`mvola.views.reconciliation_detail`: `get_reconciliation_process(process_id)` renvoie `None` → `Http404` →
redirection vers l'historique avec un message d'erreur ("Rapprochement introuvable."). Aucune logique supplémentaire
à écrire: réutiliser tel quel le pattern de `mvola/views.py`.
